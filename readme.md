# Duel Tower PRD vNext

운영용 로컬 실행/검증 절차는 `docs/local-runbook.md`를 먼저 확인한다.

* 문서 버전: vNext draft 2026-03-08
* 기준 자료: 현재 코드베이스, 업로드된 룰 시트, 현행 UI/엔진 구조
* 문서 목적: 예전의 "아이디어 설명서"가 아니라, **지금 바로 구현 우선순위를 정하는 제품 문서**로 재정의한다.

---

## 1. 제품 한 줄 정의

**Duel Tower는 고정된 룰과 카드 풀을 바탕으로, GM과 플레이어가 세션을 생성하고 참여해, 노드를 진행하고, 서버 권위 기반으로 전투를 처리하는 협동 카드 전투 웹앱이다.**

이 제품의 핵심은 "무드 좋은 설정집"이나 "범용 카드게임 엔진"이 아니라, **듀얼 타워 세션을 실제로 굴릴 수 있게 만드는 운영 도구**다.

---

## 2. 이번 PRD에서 바뀌는 방향

기존 PRD는 큰 방향을 잡는 데는 유용했지만, 범위가 넓고 추상적이었다. 지금의 프로젝트는 이미 다음과 같은 구체적 특성을 가진다.

* Spring Boot 백엔드 + Svelte SPA 프론트로 실제 플레이 루프가 존재한다.
* 세션 생성, 참가, 캐릭터 프로필, 덱 편집, 전투 커맨드, 로그, 전투 UI가 이미 이어져 있다.
* 룰상 중요한 요소인 **패 제한, 서치 선택, 이니셔티브 동률 해결, EX 쿨다운, 전투 불능, 덱 편집 제약** 등이 엔진 관점에서 구현되고 있다.
* 반면 노드/결과/인벤토리 쪽은 아직 UI 셸 성격이 강하다.

따라서 이제의 PRD는 다음처럼 초점을 옮긴다.

1. **룰 자동화가 완성된 전투 세션 루프**를 우선한다.
2. **노드-보상-보유 카드-덱 편집**을 전투와 이어지는 실제 진행 루프로 만든다.
3. 새 기능 추가보다 **지금 있는 규칙을 안정적으로 닫는 것**을 우선한다.

---

## 3. 제품 비전

플레이어와 GM이 듀얼 타워 세션을 진행할 때, 사람이 매번 손으로 계산하거나 기억해야 하는 부분을 줄이고, 다음 네 가지를 웹앱이 대신 책임진다.

* **합법성 검사**: 지금 이 행동이 가능한지 서버가 판정한다.
* **상태 전이 관리**: 덱/패/묘지/필드/제외/EX/소환물/상태를 일관되게 유지한다.
* **진행 기억**: 세션의 전투, 노드 선택, 보상 획득, 덱 변화가 기록으로 남는다.
* **운영 편의**: GM과 플레이어 모두 실수 없이 다음 단계로 진행할 수 있다.

---

## 4. 제품 원칙

### 4.1 서버 권위

모든 핵심 판정은 서버가 확정한다. 프론트는 상태를 보여주고 입력을 전달하지만, 규칙의 진실은 서버 상태다.

### 4.2 수동 계산 제거

피해, 회복, 상태 처리, 드로우, 서치, 셔플, 손패 제한, EX 쿨다운 같은 반복 계산은 서버가 처리한다.

### 4.3 강한 거부와 명확한 이유

불가능한 행동은 조용히 무시하지 않고, 왜 거부되었는지 플레이어가 바로 이해할 수 있는 오류 메시지로 반환한다.

### 4.4 고정 콘텐츠 우선

당분간은 범용 카드 제작 툴보다, 현재 룰과 카드 풀을 안정적으로 플레이할 수 있는 환경을 만드는 데 집중한다.

### 4.5 세션 운영 중심

이 제품은 혼자 즐기는 로그라이크보다, **GM이 열고 플레이어가 참가하는 세션 운영 툴**에 더 가깝다.

---

## 5. 문제 정의

현재 듀얼 타워의 실제 플레이에는 다음 문제가 있다.

1. 룰이 점점 복잡해져 사람이 모두 기억하고 처리하기 어렵다.
2. 덱/서치/셔플/토큰/EX/상태/필드/소환 처리에서 실수가 쉽게 발생한다.
3. 세션이 길어질수록 "지금 무엇을 할 수 있는지"와 "무엇이 이미 적용되었는지" 추적이 어려워진다.
4. 전투는 많이 자동화되고 있지만, 노드-보상-보유 카드-덱 편집 쪽은 아직 끊겨 있다.
5. UI가 존재하는 화면 중 일부는 아직 실제 세션 상태와 완전히 연결되지 않았다.

이 PRD의 목적은 이 문제를 해결해 **한 판의 듀얼 타워 세션을 끊김 없이 운영 가능한 제품**을 만드는 것이다.

---

## 6. 타겟 사용자

### 6.1 플레이어

* 세션에 참가한다.
* 자신의 캐릭터, 패시브, 보유 카드, 덱, EX를 기반으로 전투에 참여한다.
* 가능한 행동만 빠르게 확인하고 싶어 한다.

### 6.2 GM

* 세션을 생성하고 참가자를 모은다.
* 전투를 시작하고, 적을 조작하고, 노드 진행을 관리한다.
* 적 운영과 로그 확인을 쉽게 하고 싶어 한다.

### 6.3 개발자/운영자(본인)

* 룰 변경이 생겨도 엔진과 UI를 안정적으로 확장하고 싶다.
* 회귀 버그 없이 전투 규칙을 추가하고 싶다.

## 7. 이번 버전의 목표

## 7.1 최상위 목표

### G1. 전투 세션 루프를 완성한다

세션 생성 → 참가 → 전투 시작 → 턴 진행 → 전투 종료까지를 안정적으로 운영 가능하게 만든다.

### G2. 덱/보유 카드 운영 루프를 완성한다

보유 카드, 덱 편집, 약화/잠금/잊기 제약을 실제 세션 진행과 연결한다.

### G3. 노드 진행을 실제 세션 상태와 연결한다

현재의 노드 UI 셸을 세션 상태 기반의 진행 흐름으로 바꾼다.

### G4. 로그와 거부 메시지를 제품 수준으로 끌어올린다

왜 행동이 가능/불가능했는지, 어떤 계산이 일어났는지 사용자와 GM이 이해할 수 있어야 한다.

## 10. 핵심 사용자 시나리오

### 시나리오 A. 세션 시작

1. 사용자가 로그인한다.
2. GM이 세션을 생성한다.
3. 플레이어가 세션 코드로 참가한다.
4. 참가 시 캐릭터와 패시브, 현재 덱, EX가 확정된다.
5. 로비에서 상태를 확인하고 전투 또는 노드 진행을 시작한다.

### 시나리오 B. 전투 진행

1. GM이 전투를 시작한다.
2. 서버가 이니셔티브를 계산하고 오프닝 핸드를 지급한다.
3. 현재 턴 주체만 행동할 수 있다.
4. 플레이어 또는 GM이 카드/EX/소환 행동을 요청한다.
5. 서버가 조건을 검증하고 결과를 적용한다.
6. 패 제한, 서치 선택, 이니셔티브 동률 같은 추가 결정이 필요하면 pending decision을 발생시킨다.
7. 모든 행동은 로그에 기록된다.
8. 승패가 확정되면 전투 결과 상태로 넘어간다.

### 시나리오 C. 세션 중 덱 운영

1. 플레이어는 비전투, 비저주 상태에서 덱 편집을 연다.
2. 서버는 12장, 동일 카드 최대 3장, 보유 카드 수량, 잠긴 카드 유지, 변경 2장 제한을 검증한다.
3. 유효한 경우 새 덱을 저장하고 다음 진행에 반영한다.
4. 보유 카드가 20장을 넘었다면 잊기 처리가 선행되어야 한다.

### 시나리오 D. 노드 진행

1. 세션은 현재 노드 상태와 선택지를 가진다.
2. 플레이어들이 하나의 선택지를 선택한다.
3. 선택은 되돌릴 수 없다.
4. 선택 결과에 따라 전투, 이벤트, 저주, 보상, 시설이 이어진다.
5. 결과는 이후 보유 카드/아이템/덱 편집 가능 여부에 영향을 준다.

## 11. 기능 요구사항

## 11.1 인증 및 세션

### FR-1 로그인 기반 세션 생성

* 인증된 사용자만 세션을 생성할 수 있다.
* 세션 생성자는 GM이 된다.
* 세션은 추측이 어려운 코드와 GM 토큰을 가진다.

**완료 기준**

* 비로그인 사용자는 세션을 만들 수 없다.
* GM 식별자는 인증 사용자와 일치해야 한다.

### FR-2 로그인 기반 세션 참가

* 인증된 사용자만 세션에 참가할 수 있다.
* 플레이어는 자신의 아이디로만 참가할 수 있다.
* 참가 시 캐릭터 ID 또는 프리셋 정보로 초기 상태를 구성한다.

**완료 기준**

* 다른 사람 이름으로 참가할 수 없다.
* 최초 참가 시 패시브는 고정되며 이후 바꿀 수 없다.

### FR-3 세션 상태 조회

* 프론트는 현재 세션 상태를 주기적으로 가져오거나 푸시로 받는다.
* 상태에는 버전, 플레이어 상태, 전투 상태, 카드 인스턴스, pending decision이 포함된다.

**완료 기준**

* 클라이언트는 최신 상태 버전을 항상 보유한다.
* 커맨드는 expectedVersion과 함께 전송된다.

---

## 11.2 캐릭터 / 패시브 / 보유 카드 / 덱

### FR-4 캐릭터 프로필 관리

* 캐릭터는 기본 프로필, 능력치, EX, 패시브, 보유 카드를 가진다.
* 캐릭터 기반 참가 시 서버 데이터가 우선한다.

### FR-5 패시브 선택 및 고정

* 캐릭터 특성은 최대 2개까지 허용한다.
* 참가 이후 세션 도중 재설정할 수 없다.

### FR-6 보유 카드 제한

* 한 캐릭터의 보유 카드는 최대 20장이다.
* 20장을 넘으면 잊기 처리 전까지 일부 행동이 막힌다.

### FR-7 잊기 규칙

* 강화/약화/덱 고정 카드, 현재 덱 유지에 필요한 카드는 잊을 수 없다.
* 잊기 가능한 카드만 제거 가능하다.

### FR-8 덱 편집

* 덱은 정확히 12장이어야 한다.
* 동일 카드 3장 초과는 금지한다.
* 보유하지 않은 카드는 넣을 수 없다.
* 현재 목표 버전에서는 비전투, 비저주 상태에서만 편집 가능하다.
* 별도 언급이 없는 한 한 번의 편집에서 바꿀 수 있는 카드는 최대 2장이다.
* 약화/잠금으로 인해 덱에 남아야 하는 카드는 제거할 수 없다.

**완료 기준**

* 잘못된 덱 저장 시 이유가 명확히 반환된다.
* 합법적인 덱 변경은 캐릭터 현재 덱에도 반영된다.

---

## 11.3 전투 엔진

### FR-9 전투 시작

* GM이 전투를 시작할 수 있다.
* 전투 시작 시 각 참여자는 오프닝 핸드 4장을 가진다.
* 이니셔티브를 계산하여 턴 순서를 확정한다.
* 플레이어 간 동률은 추가 결정을 요구한다.
* 플레이어와 적이 동률일 경우 플레이어 우선 규칙을 따른다.

### FR-10 턴 흐름

* 현재 턴 주체만 행동할 수 있다.
* 턴 시작 드로우 규칙은 다음을 따른다.

    * 손패 4장 미만이면 2장
    * 아니면 1장
* 턴 종료 시 상태 및 라운드 진행 처리를 수행한다.

### FR-11 카드 사용

* 플레이어는 손패 카드 사용을 요청할 수 있다.
* 서버는 코스트, 대상, 상태, 키워드, 현재 페이즈를 검증한다.
* 성공 시 효과 적용 후 카드 이동을 처리한다.

### FR-12 EX 사용

* 각 플레이어는 자신의 EX 카드를 별도 존에서 사용한다.
* EX는 사용 후 다음 라운드 종료 시점까지 비활성화된다.
* 스킬 카드 대상 효과는 EX에 적용되지 않는다.

### FR-13 패 교환

* 플레이어는 자신의 턴에 패 교환을 1회 사용할 수 있다.
* 카드 1장을 버리고 1장을 뽑는다.
* 버린 카드가 토큰이면 추가 드로우를 하지 않는다.

### FR-14 손패 제한

* 손패 최대치는 6장이다.
* 초과 시 즉시 pending decision을 생성하고, 해결 전까지 일반 행동을 막는다.

### FR-15 덱 리필 및 드로우 실패

* 덱이 비었을 때 묘지를 섞어 새 덱을 만든다.
* 필요한 드로우 수보다 덱이 부족하면 남은 카드를 먼저 뽑고 리필 후 부족분을 채운다.
* 일반 드로우 자체가 불가능하면 이번 전투 동안의 전투 불능 상태를 부여한다.

### FR-16 상태 처리

* 강화/약화/도발/회피/보호/방벽/재생/활력/기절/중압/혼란/고통/파괴/쇠약/취약 등 지원 대상 상태를 처리한다.
* 상태는 턴 시작, 턴 종료, 라운드 경계 등 정의된 시점에 갱신된다.
* 값이 0이 되면 상태는 제거된다.

### FR-17 키워드 처리

* 설치, 소환, 제외, 부동, 명경, 필중, 관통, 집념, 치명, 증강, 충전 등 현재 지원 범위를 서버가 처리한다.
* 파라미터형 키워드의 수치 해석은 서버가 맡는다.

### FR-18 피해/회복 파이프라인

* 대상 확정
* 치명 체크
* 공격자 상태/진영 효과
* 대상 진영/상태 효과
* 최종 피해/회복 적용
  순서로 계산한다.

### FR-19 소환/설치/토큰

* 설치/소환 카드는 필드에 남는다.
* 필드는 플레이어별로 분리되며 최대 5장을 넘을 수 없다.
* 토큰은 손패/필드 밖으로 이동하면 소멸한다.
* 소환물은 독립적인 대상이 될 수 있고 자체 스탯과 액션 가능 상태를 가진다.

### FR-20 적 조작

* 현재 목표 버전에서는 적 AI 대신 GM 수동 조작을 지원한다.
* GM은 적 카드 사용, 적 EX 사용, 적 턴 종료를 수행할 수 있다.

### FR-21 전투 종료와 전투 불능 유지 규칙

* 체력 0 기반 전투 불능은 해제 전까지 유지된다.
* 덱 소진 기반 전투 불능은 전투 종료 후 초기화 규칙을 분리해서 관리한다.
* 새 전투 시작 시 무엇이 유지되고 무엇이 초기화되는지 서버가 일관되게 보장해야 한다.

### FR-22 전투 로그

* 카드 사용, 피해, 회복, 상태 증감, 턴 전환, pending decision 생성/해제, 셔플, 드로우, 전투 종료를 로그에 남긴다.
* 사용자용 요약과 개발/검증용 상세를 모두 제공할 수 있어야 한다.

### FR-23 세션 상태 기반 노드 관리

* 세션은 현재 노드 상태와 선택 가능한 다음 노드 목록을 가진다.

### FR-24 단일 선택과 비가역성

* 각 노드에서 선택지는 1개만 확정 가능하다.

### FR-25 노드 타입

* 최소한 다음 타입을 지원 대상으로 둔다.

    * 아무것도 없음
    * 시설
    * 저주
    * 전투
    * 보스
    * 이벤트/판정
    * ???

### FR-26 노드와 전투의 연결

* 전투 노드 선택 시 실제 세션 전투 상태가 시작된다.
* 전투 종료 후 결과에 따라 다음 노드 혹은 실패 처리로 이동한다.

### FR-27 저주와 덱 편집 제한

* 저주 관련 상태에서는 덱 편집이 막힌다.
* 노드 상태는 UI 연출이 아니라 서버 규칙과 연결되어야 한다.

### FR-31 명확한 오류 메시지

* 특히 전투 재시작, 전투 불능 지속성, EX 쿨다운, 서치, 손패 제한, 적 턴 검증 등은 회귀 테스트 핵심 영역이다.

## 16. 성공 지표

### 제품 성공 지표

1. 한 번의 세션에서 전투 시작부터 종료까지 수동 개입 없이 진행 가능한가
2. 플레이어가 "왜 이 행동이 안 되는지"를 로그/오류만 보고 이해 가능한가
3. 덱 편집 규칙 위반과 전투 규칙 위반이 서버에서 안정적으로 차단되는가
4. 노드 선택 이후 전투/결과/보상 흐름이 끊기지 않는가

### 개발 성공 지표

1. 전투 회귀 테스트가 핵심 규칙을 보호하는가
2. 새 카드/상태/키워드 추가 시 기존 규칙이 깨지지 않는가
3. 프론트 화면이 더미 상태가 아니라 실제 세션 상태에 연결되는가

## 19. P0 백로그 (실행 단위)

아래 백로그는 현재 업로드된 코드/룰 기준으로, **지금 바로 이슈로 쪼개서 진행할 수 있는 수준**으로 정리한 것이다.

### EPIC P0-1. 전투 재시작과 전투 불능 규칙 고정

#### P0-1-1. 체력 0 기반 전투 불능과 덱 소진 기반 전투 불능을 분리 정착

* 문제

    * 전투 불능에는 전투 간 유지되어야 하는 경우와 전투 종료 시 초기화되어야 하는 경우가 섞여 있다.
    * 현재 회귀 테스트에서도 이 구분이 핵심 보호 대상이다.
* 목표

    * `BATTLE_INCAPACITATED_PERSISTENT`와 `BATTLE_INCAPACITATED`의 생명주기를 명확히 분리한다.
* 완료 기준

    * 체력 0 기반 전투 불능은 전투 재시작 후에도 유지된다.
    * 덱 소진 기반 전투 불능은 전투 재시작 후 초기화된다.
    * 새 전투 시작 시 지속 전투 불능 플레이어는 턴 오더와 오프닝 드로우에서 제외된다.
* 주요 파일

    * `engine/core/combat/CombatEntityOps.java`
    * `engine/core/combat/VictoryOps.java`
    * `engine/command/StartCombatCommand.java`
    * `engine/command/DrawCommand.java`
    * `engine/RuleEngineRegressionTest.java`

#### P0-1-2. 전투 시작 초기화 규칙 표준화

* 문제

    * 새 전투 시작 시 무엇을 초기화하고 무엇을 유지하는지 코드상 진입점이 흩어질 가능성이 있다.
* 목표

    * 전투 시작 초기화 규칙을 한 곳에서 설명 가능한 수준으로 정리한다.
* 완료 기준

    * StartCombat 시 초기화 목록이 문서와 테스트로 고정된다.
    * EX 쿨다운, 턴 관련 일시 상태, pending decision, 드로우 가능 상태의 초기화 범위가 명확하다.
* 산출물

    * 전투 시작 초기화 체크리스트
    * 회귀 테스트 3개 이상 추가

### EPIC P0-2. pending decision 흐름 완성

#### P0-2-1. 손패 제한 강제 버리기 UX/서버 규칙 일치

* 문제

    * 손패 제한은 서버에서 pending decision을 생성하지만, 실제 플레이에서 "왜 막혔는지"와 "무엇을 버릴 수 있는지"의 안내가 더 선명해야 한다.
* 목표

    * 서버와 프론트 모두에서 손패 제한 처리 경험을 완성한다.
* 완료 기준

    * pending decision 존재 시 일반 행동이 차단된다.
    * 부동 카드만 있는 경우, 실제 룰대로 예외 처리된다.
    * 프론트에서 선택 개수 제한과 제출 가능 상태가 명확히 보인다.
* 주요 파일

    * `engine/core/HandLimitOps.java`
    * `engine/command/DiscardToHandLimitCommand.java`
    * `engine/command/CommandValidation.java`
    * `duel-tower-ui/src/routes/Combat.svelte`

#### P0-2-2. 이니셔티브 동률 해결 플로우 마감

* 문제

    * 현재 엔진에는 동률 그룹과 해결 커맨드가 있지만, 실전 UX 관점에서 전체 흐름을 더 닫아야 한다.
* 목표

    * 동률 발생 → 순서 지정 → 모든 동률 해소 → 턴 시작 흐름을 일관되게 만든다.
* 완료 기준

    * 동률 플레이어 모두에게 적절한 pending decision이 생성된다.
    * 잘못된 그룹 인덱스/멤버 조합/중복 응답이 모두 방어된다.
    * 프론트에서 순서 조정과 확정이 가능하다.
* 주요 파일

    * `engine/command/StartCombatCommand.java`
    * `engine/command/ResolveInitiativeTieCommand.java`
    * `duel-tower-ui/src/routes/Combat.svelte`

#### P0-2-3. 서치 선택 pending decision 공통화 점검

* 문제

    * 검색/선택형 효과가 늘어나면 SearchPick 계열 흐름이 다른 pending decision과 충돌하기 쉽다.
* 목표

    * SearchPick을 hand limit / initiative tie와 같은 공통 규칙으로 묶는다.
* 완료 기준

    * 동시에 둘 이상의 pending decision이 생성되지 않는다.
    * SearchPick 해결 후 상태/로그/버전이 정상 갱신된다.
* 주요 파일

    * `engine/core/SearchPickOps.java`
    * `engine/command/ResolveSearchPickCommand.java`
    * 관련 테스트 전부

### EPIC P0-3. 덱 편집 / 보유 카드 / 잊기 루프 제품화

#### P0-3-1. 덱 편집 규칙을 세션 기능으로 고정

* 문제

    * 현재 덱 편집은 이미 강한 제약을 가지지만, 제품 입장에서는 "왜 저장이 안 되는지"가 더 직접적으로 보여야 한다.
* 목표

    * 덱 편집을 단순 CRUD가 아니라 규칙 기반 세션 액션으로 고정한다.
* 완료 기준

    * 다음 규칙이 모두 테스트와 UI 메시지로 보장된다.

        * 정확히 12장
        * 동일 카드 최대 3장
        * 보유 카드 수량 초과 불가
        * 전투 중 불가
        * 저주 상태 불가
        * 변경 2장 초과 불가
        * locked-in-deck 카드 제거 불가
* 주요 파일

    * `session/service/SessionService.java`
    * `content/deck/service/DeckService.java`
    * `duel-tower-ui/src/routes/DeckEdit.svelte`
    * `session/api/SessionDeckRuleIntegrationTest.java`

#### P0-3-2. 보유 카드 20장 초과 시 잊기 강제 루프 닫기

* 문제

    * 현재 forgettingRequired와 forget API는 존재하지만, 노드/보상과 이어지는 실제 플레이 루프가 아직 약하다.
* 목표

    * 카드 획득 직후 20장 초과 여부를 검사하고, 잊기 완료 전 다른 진행을 제한한다.
* 완료 기준

    * 20장 초과 즉시 `forgettingRequired=true`가 된다.
    * 덱 편집 및 다음 진행 진입이 적절히 차단된다.
    * 잊기 가능 카드가 없을 때 명시적인 오류를 준다.
* 주요 파일

    * `engine/model/PlayerState.java`
    * `session/service/OwnedCardForgetPolicy.java`
    * `session/service/SessionService.java`
    * `session/api/SessionDeckRuleIntegrationTest.java`

#### P0-3-3. 덱 편집/잊기 화면을 실제 세션 상태에 연결

* 문제

    * 프론트는 레이아웃이 이미 있으나, 제품적으로는 아직 "규칙 기반 편집기"보다 "보기 좋은 목업"에 가까운 부분이 남아 있다.
* 목표

    * 서버 응답을 그대로 쓰는 실전용 덱 운영 화면으로 바꾼다.
* 완료 기준

    * 현재 덱, 보유 카드, 잠금/강화/약화 상태, 편집 불가 사유, 잊기 필요 여부가 모두 표시된다.
    * 실패 응답이 토스트가 아니라 화면 레벨 피드백으로도 드러난다.
* 주요 파일

    * `duel-tower-ui/src/routes/DeckEdit.svelte`
    * `duel-tower-ui/src/stores/session.ts`
    * `duel-tower-ui/src/lib/model.ts`

### EPIC P0-4. Node / Results / Inventory의 더미 상태 제거

#### P0-4-1. Node를 하드코딩 목록에서 세션 상태 기반으로 전환

* 문제

    * 현재 Node 화면은 정적 배열(`N-1`, `N-2` 등) 기반이다.
    * 이 상태로는 실제 런 진행과 연결되지 않는다.
* 목표

    * 현재 노드, 선택지, 진입 가능 여부, 선택 후 결과가 세션 상태에 존재하도록 만든다.
* 완료 기준

    * 프론트의 정적 노드 배열이 제거된다.
    * 세션 상태 DTO에 현재 노드/선택지 정보가 포함된다.
    * 선택 확정은 서버 API를 통해 처리된다.
* 주요 파일

    * `engine/model/GameState.java`
    * `engine/model/NodeState.java`
    * `session/dto/SessionStateDto.java`
    * `session/service/SessionService.java`
    * `session/api/SessionController.java`
    * `duel-tower-ui/src/routes/Node.svelte`

#### P0-4-2. Results를 exploration store 임시 상태에서 서버 결과 기반으로 전환

* 문제

    * 현재 Results는 `explorationResult` 스토어의 임시 데이터에 강하게 의존한다.
* 목표

    * 전투 종료/판정 성공·실패/보상 획득 결과를 서버 상태 또는 서버 응답 이벤트로 일관되게 표현한다.
* 완료 기준

    * 결과 카드는 서버에서 온 데이터만으로 렌더링 가능하다.
    * 새로고침 후에도 최근 결과를 재구성할 수 있다.
* 주요 파일

    * `duel-tower-ui/src/stores/exploration.ts`
    * `duel-tower-ui/src/routes/Results.svelte`
    * `session/dto/EngineResponseDto.java`
    * `session/runtime/StateMapper.java`

#### P0-4-3. Inventory를 실제 세션 자원과 연결

* 문제

    * 현재 Inventory는 고정 슬롯 데이터 기반이다.
* 목표

    * 최소 범위라도 열쇠/상자/재료/전투 사용 가능 아이템을 세션 상태로 노출한다.
* 완료 기준

    * 프론트의 하드코딩 슬롯 배열이 제거된다.
    * SessionState 또는 별도 인벤토리 DTO에서 데이터를 받아 렌더링한다.
    * Node/Results와 인벤토리 증감이 연결된다.
* 주요 파일

    * `session/dto/*`
    * `engine/model/*` 또는 런 상태 모델 신설
    * `duel-tower-ui/src/routes/Inventory.svelte`

## 21. 이 백로그의 핵심 판단

현재 코드 기준으로 가장 먼저 없애야 할 것은 "룰이 없는 기능"보다 **서버 룰은 있는데 프론트와 세션 루프가 아직 완전히 닫히지 않은 부분**이다.

즉, 새 기능을 더 넣기 전에 아래 세 가지를 먼저 닫는 것이 맞다.

1. 전투 재시작/전투 불능/결정 대기 같은 엔진 핵심 규칙
2. 보유 카드/덱 편집/잊기 같은 세션 지속 규칙
3. Node/Results/Inventory의 하드코딩 UI를 실제 상태 기반 화면으로 전환

## 22. 이번 시점의 오픈 이슈

1. 노드 상태와 런 상태를 어디까지 서버 영속 상태로 둘 것인가
2. 결과/보상 데이터를 세션 상태, 프로필 상태, 별도 런 상태 중 어디에 저장할 것인가
3. 캐릭터 시트의 편집 범위와 세션 중 수정 가능 범위를 어떻게 자를 것인가
4. 적 콘텐츠와 노드 콘텐츠를 코드 고정으로 둘지, 데이터 파일 기반으로 옮길지
5. 웹소켓 도입 시점과 폴링 제거 시점은 언제가 적절한가

## 20. 결론

지금 Duel Tower의 목표는 "언젠가 멋진 카드게임 플랫폼 만들기"가 아니다.

**지금 당장 필요한 목표는, 현재 룰과 현재 콘텐츠를 기준으로 듀얼 타워 세션을 실제로 끝까지 운영할 수 있는 서버 권위형 웹앱을 완성하는 것**이다.

따라서 앞으로의 우선순위는 다음 한 줄로 요약한다.

**전투 엔진을 안정화하고, 노드-보상-보유 카드-덱 편집을 한 세션 루프로 닫는다.**
